CipherLink - outstanding information

To run measured Phase 14-15 traffic analysis on your computer, I still need these environment details or the generated capture report:

1. Install Wireshark with TShark, then confirm `tshark --version` works in PowerShell.
2. Run `python traffic-analysis/capture.py --list-interfaces` and choose the network interface used for your CipherLink traffic (for example, Wi-Fi or Ethernet).
3. Live packet capture may require running PowerShell as Administrator. Capture only traffic you are authorized to inspect.
4. To populate the dashboard with real measurements, run a capture while performing a defined CipherLink test and then analyze it. You can load the generated `.analysis.json` into `/traffic-analysis`, or provide the report if you want me to review the metrics.
5. If you want a specific experiment, provide its capture duration, traffic filter, and whether to capture browser/client traffic or traffic on a backend you control. Otherwise the provided commands use a 60-second capture and `port 443` filter.

Implemented in Phases 14-15:
- PyShark live PCAPNG capture with interface listing, duration, and optional BPF capture filter.
- Offline PCAP/PCAPNG analyzer for packet count and size, protocols, endpoints, TCP retransmissions, TCP ACK RTT samples, total bytes, duration, throughput, and time series.
- JSON report for the website dashboard and optional per-packet CSV export.
- `/traffic-analysis` page with metric cards, packet/time and throughput/time charts, packet-size and protocol distributions, TCP ACK RTT vs packet size, and top network flows.
- The dashboard accepts measured JSON reports and does not invent sample values.

Important measurement note: a capture of the hosted HTTPS/WSS site normally shows TLS packet metadata and ciphertext traffic, not chat plaintext. TCP ACK RTT is a transport-level estimate, not end-to-end application latency. PCAPs/reports can contain IP addresses and timing metadata; keep them private.

Security note: the Phase 5-15 prototype encrypts chat text and image chunks in the browsers with AES-256-GCM. The key exchange is not authenticated automatically; partners should compare fingerprints through a separate trusted channel. Image transfer is limited to 10 MB. The chat displays a SQLite-backed hash-chain event log and checks its integrity; this detects record edits but is not a signed or externally anchored proof. API request throttling and replay tracking use in-memory state and reset when the backend restarts. Later phases still include packet-sniffing demonstrations, tampering/replay/impersonation/flooding experiments, image-security metrics, performance benchmarks, a final security dashboard, and evaluation/reporting.
